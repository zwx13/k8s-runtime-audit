`01-cross-tenant-access.sh` The first script tests cross-tenant access. It creates a ClusterRole and namespace-scoped RoleBindings for two groups, each belonging to a separate tenant. One of the bindings is intentionally misconfigured so that a user belonging to one tenant is able to access resources in the namespace of another tenant. This violates the selected multitenancy policy and produces an alert in the NATS alert stream. The alert is also printed to the terminal and saved in the results folder.

`02-dangling-rolebinding.sh` The second script tests dangling RoleBindings. It first creates a ClusterRole, then creates a RoleBinding that references it. Then, the script deletes the referenced ClusterRole. As a result, the RoleBinding remains in the namespace but poits to a role that no longer exists. The checker detects this dangling reference and emits an alert.

`03-rolebinding-to-cluster-admin.sh` The third script tests namespace scoped grants to `cluster-admin`. It creates a RoleBinding in a tenant namespace which points to the default `cluster-admin` ClusterRole. In the multitenancy model used in this thesis, tenant namespace access must not grant cluster administrator privileges. As a result, the event is treated as a policy violation and produces an alert.

`04-clusterrolebinding-to-tenant-group.sh` The fourth script tests cluster-wide grants to tenant groups. It creates a ClusterRoleBinding that grants a cluster-level role to a tenant group, which our multitenancy model prohibits since we reserve cluster-wide permissions for platform-level groups. Therefore, granting such permissions to a tenant group violates the policy and is reported by the checker.

`05-dangling-clusterrolebinding.sh` The fifth script tests dangling ClusterRoleBindings. This scenario is similar to the dangling RoleBindings case, but it is cluster-scoped. The script creates a ClusterRole, creates a ClusterRoleBinding that references it, and then deletes the references ClusterRole. The remaining ClusterRoleBinding becomes dangling, and the checker emits an alert.

`06-combined-scenario.sh` The final script evaluates the checker under less controlled event interleavings. Instead of executing a single fixed scenario, it uses a loop to generate a configurable number of random events where each event may correspond to one of the previously described violation types. This is meant to approximate a more realistic cluster setting, where different actors may perform actions independently, and events do not appear in a predetermined sequence. As a result, the script may lead to multiple alerts being output in a single run.
